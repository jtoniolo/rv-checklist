# Service workers for Next.js on OpenNext / Cloudflare Workers

Scope: viable ways to add a full service worker (app-shell precache, offline fallback, runtime caching) to this app — Next.js ~16.1.6 deployed with `@opennextjs/cloudflare` ^1.20.2 (`main: .open-next/worker.js`, `assets: .open-next/assets` with `ASSETS` binding). Compares Serwist, next-pwa forks, and a hand-rolled SW. For GitHub issue #125.

Date compiled: 2026-08-20

Source priority: official docs (Serwist, OpenNext, Cloudflare, Next.js), project source code (unpkg/raw GitHub), and project issue trackers only. No blog posts. Claims not confirmed by a primary source are marked **unverified**.

## 1. Does OpenNext emit and serve the SW file correctly?

**Files in `public/` become Workers static assets.** The OpenNext Cloudflare static-assets guide confirms files from Next's `public` folder are served via Workers Static Assets from `.open-next/assets` through the `ASSETS` binding ([OpenNext assets howto](https://opennext.js.org/cloudflare/howtos/assets)). So any SW built into `public/` (hand-rolled, or `@serwist/next`'s webpack output `swDest: "public/sw.js"` — [Serwist getting started](https://serwist.pages.dev/docs/next/getting-started)) ends up in `.open-next/assets/sw.js` and is served at `/sw.js`.

**Headers are correct by default.** Workers static assets responses get `Content-Type` from the file extension (set by Wrangler at upload), `Cache-Control: public, max-age=0, must-revalidate`, an `ETag`, and `CF-Cache-Status` ([Cloudflare Workers static assets headers](https://developers.cloudflare.com/workers/static-assets/headers/)). `max-age=0, must-revalidate` is exactly what you want for `sw.js` (browser revalidates on every SW update check; matches the Next.js guide's own recommendation of `no-cache` semantics for `/sw.js` — [Next.js PWA guide](https://nextjs.org/docs/app/guides/progressive-web-apps)). Registering with `updateViaCache: "none"` (as the Next.js guide shows) removes any residual HTTP-cache concern.

**`Service-Worker-Allowed` is not needed** when the SW sits at the asset root (`/sw.js`): its default max scope is already `/`. Cloudflare's headers doc has no special handling for it, but `_headers`/`_redirects` files are natively supported by Workers static assets if a custom header were ever required ([migration guide](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/), [headers doc](https://developers.cloudflare.com/workers/static-assets/headers/)).

**Caveat: `next.config` `headers()` do not apply to assets in the default mode.** With `run_worker_first: false` (the default), asset requests "are intercepted before reaching the worker" — no middleware, no Next.js headers/rewrites apply; custom headers must go through Workers Static Assets (`_headers`) instead ([OpenNext assets howto](https://opennext.js.org/cloudflare/howtos/assets)). The header recipe in the Next.js PWA guide (per-route `headers()` for `/sw.js`) therefore does nothing here — but as shown above the Workers defaults are already correct.

**Turbopack path is different:** `@serwist/turbopack` does not emit a static file. It serves the compiled SW from a route handler (`app/serwist/[path]/route.ts`, `createSerwistRoute`, registered at `/serwist/sw.js` — [Turbopack guide](https://serwist.pages.dev/docs/next/turbo)). The handler compiles with esbuild at build time (`generateStaticParams`, `dynamic: "force-static"`, `revalidate: false`) and responds with `Content-Type` and `Service-Worker-Allowed: "/"` so the out-of-root SW can still claim scope `/` ([package source, v9.5.12](https://unpkg.com/@serwist/turbopack@9.5.12/src/index.ts)). On OpenNext this request is an asset miss, so it goes through the Worker; that works, but it means **the SW URL passes through Next middleware** (see §2) and the prerendered-route-handler serving path on OpenNext is **unverified** (no OpenNext doc or issue covers it; it should behave like any other force-static route).

## 2. Coexistence with per-request SSR and auth middleware

These interactions follow from standard service-worker semantics (the SW's `fetch` handler intercepts in-scope navigations and subresource requests; responses served from Cache Storage never reach the server — [MDN Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)) applied to this app's architecture (ADR-0018: per-request SSR, edge middleware refreshing tokens via Set-Cookie). Points below are analysis grounded in those primary sources, not platform-specific bugs.

- **Cached navigations bypass the middleware.** Any navigation the SW answers from cache skips the server entirely, so the middleware's auth guard and token refresh do not run for that navigation. If SSR HTML were served cache-first, a user could sit on cached pages while their refresh token quietly expires. Mitigation: use **NetworkFirst** for documents/RSC (Serwist's `defaultCache` does exactly this — see §3a) so the middleware runs on every online navigation and cache is only a fallback.
- **Do not precache or CacheFirst-cache SSR HTML.** Per-request, per-user HTML in Cache Storage risks showing stale or another-session state after sign-out (Cache Storage is not cleared by cookie expiry). `Set-Cookie` headers themselves are not a leak vector — `Cache.put` stores the response body/headers the page received, but the concern is stale authenticated content. Serwist's `defaultCache` bounds this (32 entries, 24 h, NetworkFirst), but a stricter policy for this app is NetworkOnly for documents plus a dedicated offline fallback page.
- **Offline fallback works fine with SSR.** The standard pattern is a static offline page (Serwist: `fallbacks.entries` matching `request.destination === "document"`, with a precached `/~offline` route — [example sw.ts](https://github.com/serwist/serwist/tree/main/examples/next-basic)). The fallback page must be a route that renders without auth, or middleware must allow it, since it gets precached at SW install time by a fetch that passes through the middleware.
- **Navigation preload** (`navigationPreload: true` in Serwist's example config) makes the browser start the network navigation request in parallel with SW startup ([MDN NavigationPreloadManager](https://developer.mozilla.org/en-US/docs/Web/API/NavigationPreloadManager)). The preload request is a real server request, so middleware runs on it normally; it only helps latency for network-served SSR pages. No conflict.
- **Middleware must not intercept the SW script URL.** SW script fetches must not be answered with a redirect (registration fails). With the webpack/hand-rolled path (`/sw.js` in assets, `run_worker_first: false`) middleware never sees the request — nothing to do. With `@serwist/turbopack` (`/serwist/sw.js` served by the Worker), the auth middleware matcher must exclude `/serwist/*` or the login redirect breaks SW installation/updates. (Consequence of the OpenNext asset-interception behavior above plus the middleware's own config; app-specific, so verify in the middleware matcher.)

## 3. Precache versioning across deploys

**a) How the manifest is built.** `@serwist/next` (webpack) and both next-pwa lineages use Workbox-style InjectManifest: the build plugin scans the compiled `.next` output (hashed `_next/static/*` files) and injects the URL+revision list as `self.__SW_MANIFEST`, which the SW passes to `precacheEntries` ([Serwist getting started](https://serwist.pages.dev/docs/next/getting-started), [example sw.ts](https://github.com/serwist/serwist/tree/main/examples/next-basic)). `@serwist/turbopack` injects the same `__SW_MANIFEST` from its esbuild step at `generateStaticParams` time ([Turbopack guide](https://serwist.pages.dev/docs/next/turbo), [source](https://unpkg.com/@serwist/turbopack@9.5.12/src/index.ts)); its example uses `git rev-parse HEAD` as the revision for non-hashed entries ([example route.ts](https://github.com/serwist/serwist/tree/main/examples/next-turbo-basic)). Runtime caching defaults (`defaultCache` from `@serwist/next/worker`): NetworkOnly in dev; in production NetworkFirst for HTML documents and RSC requests (32 entries / 24 h), CacheFirst for `_next/static` JS (64 entries / 24 h), StaleWhileRevalidate for images, NetworkFirst with 10 s timeout for same-origin `/api/*` GET, NetworkOnly for `/api/auth/*` ([source: packages/next/src/index.worker.ts](https://raw.githubusercontent.com/serwist/serwist/main/packages/next/src/index.worker.ts)).

**b) What happens to old hashed assets after a deploy.** Cloudflare Workers deployments are atomic units; the docs do not describe any serving of prior asset versions ([Workers static assets](https://developers.cloudflare.com/workers/static-assets/)). OpenNext's skew-protection howto confirms the failure mode directly: without it, "old hashed assets may become inaccessible after new deployments" — i.e. a client holding old HTML that requests old `_next/static` chunks gets 404s ([OpenNext skew howto](https://opennext.js.org/cloudflare/howtos/skew)). Consequences for a SW:

- A SW **helps** here: chunks precached or CacheFirst-cached before the deploy keep working from Cache Storage even after the server 404s them. This is a point in favor of precache for `_next/static`.
- The new SW's install fetches the **new** manifest URLs (which exist on the new deployment), so precache-on-update does not race the deploy; Workbox-lineage precaching deletes outdated precache entries on activate.
- OpenNext's skew protection (experimental; routes requests to previous versions via preview URLs; requires `run_worker_first: true`, env vars, and is incompatible with Durable-Object-hosting Workers) is an alternative/complement, but it changes the asset-serving mode and billing ([skew howto](https://opennext.js.org/cloudflare/howtos/skew), [assets howto](https://opennext.js.org/cloudflare/howtos/assets)).

**c) skipWaiting/clientsClaim.** Serwist's official Next example enables `skipWaiting: true, clientsClaim: true` ([example sw.ts](https://github.com/serwist/serwist/tree/main/examples/next-basic)), so a new SW takes control of open tabs immediately after install. Combined with 24 h max-age on the runtime page cache and NetworkFirst navigation, this bounds how long stale assets/pages persist. With `skipWaiting`, a tab can end up running old page JS against a new SW's caches; the precache cleanup on activate is what makes old-chunk survival across deploys best-effort rather than guaranteed.

## 4. OpenNext/Cloudflare-specific pitfalls (issue-tracker sweep)

- **`opennextjs/opennextjs-cloudflare` issues:** GitHub issue search on 2026-08-20 for `pwa` and for `serwist`/`next-pwa`/`sw.js` returned **0 results**; a search for `"service worker"` returned 51 hits that are all about Cloudflare **service bindings** / Workers runtime, none about browser service workers ([issue search](https://github.com/opennextjs/opennextjs-cloudflare/issues)). So: no known adapter-level SW bugs, but also no documented support surface — nobody has filed anything either way.
- **`serwist/serwist` issues:** searching `cloudflare` returned only a release PR noting Serwist's own docs deploy on Cloudflare Pages ([serwist issue search](https://github.com/serwist/serwist/issues)); no Cloudflare/OpenNext integration issues. Relevant Turbopack history: [#54](https://github.com/serwist/serwist/issues/54) (Turbopack support, resolved Dec 2025 by backporting `@serwist/turbopack` to Serwist 9) and [#294](https://github.com/serwist/serwist/issues/294) (`__SW_MANIFEST` not injected — filed against the v10 **preview**, closed as not planned; the stable 9.5.x line is what's current).
- **Asset headers can't come from `next.config`** in default mode (see §1) — use `_headers` in the assets directory if ever needed ([OpenNext assets howto](https://opennext.js.org/cloudflare/howtos/assets), [Cloudflare `_headers`](https://developers.cloudflare.com/workers/static-assets/headers/)).
- **Bundler choice is forced by Next 16:** Turbopack is the default bundler for `next build`; webpack requires an explicit `next build --webpack` opt-out ([Next.js 16 release notes](https://nextjs.org/blog/next-16)). OpenNext Cloudflare supports Turbopack compilation ([OpenNext Cloudflare index](https://opennext.js.org/cloudflare)). So `@serwist/next` (webpack plugin) would force this repo onto `--webpack` builds; `@serwist/turbopack` keeps the default pipeline.
- **Unverified:** how OpenNext serves a `force-static` route handler's custom headers (`Service-Worker-Allowed`) — no primary source found; needs a smoke test if the Turbopack path is chosen. Also the exact release date of `next-pwa` 5.6.0 (registry `time` field wasn't retrievable; the latest-version fact itself is confirmed).

## Recommendation for rv-checklist

Two viable paths; both avoid the dormant next-pwa lineage:

1. **Serwist via `@serwist/turbopack` 9.5.12** — keeps the default Next 16 Turbopack build, gives precache manifest + `defaultCache` + offline fallback out of the box. Requires: middleware matcher exclusion for `/serwist/*`, a smoke test that the force-static route serves `Service-Worker-Allowed: /` through OpenNext, and overriding `defaultCache`'s document/RSC entries to NetworkOnly (or a tightened NetworkFirst) given per-request auth SSR.
2. **Hand-rolled SW in `public/sw.js`** — smallest surface and the most predictable on OpenNext (static asset, correct headers by default, never touches middleware). You give up automatic precache-manifest generation; app-shell precache would be limited to stable URLs (offline page, icons) plus runtime CacheFirst for `_next/static`, which — given every signed-in page is server-rendered anyway — covers most of the real offline value.

For this app, start with option 2 unless full hashed-asset precache is a hard requirement; its serving story has zero unverified steps. Adopt Serwist/Turbopack if the precache manifest and Workbox-grade caching strategies earn their integration risk.

Either way: NetworkFirst-or-NetworkOnly for documents/RSC so the auth middleware always runs when online; precached static offline fallback page reachable without auth; `updateViaCache: "none"` on registration; rely on Workers Assets' default `max-age=0, must-revalidate` for the SW script.
