# Service Workers for Next.js on OpenNext / Cloudflare Workers

**Scope:** Viable ways to add a full service worker (SW) — app-shell precache, offline fallback, runtime caching — to a Next.js app deployed with `@opennextjs/cloudflare` on a Cloudflare Worker. Compares Serwist, next-pwa (both forks), and a hand-rolled SW. Answers GitHub issue [#125](https://github.com/jtoniolo/rv-checklist/issues/125).

**Date compiled:** 2026-08-20

**Source-priority note:** All claims come from primary sources: Serwist docs and its GitHub issue tracker, OpenNext Cloudflare docs and its issue tracker, Cloudflare Workers docs, Next.js docs, and repository metadata read through the GitHub API. No blog posts. Claims not verified against a primary source are marked **unverified**.

**Repo context (verified in this repo, not researched):** Next.js `~16.1.6`, `@opennextjs/cloudflare` `^1.20.2`. Deploy is `opennextjs-cloudflare build` then `wrangler deploy`; `apps/web/wrangler.jsonc` sets `main: .open-next/worker.js` and `assets: { directory: .open-next/assets, binding: ASSETS }`. `apps/web/package.json` has no `build` script, so the OpenNext build runs `next build` with the Next 16 default bundler (Turbopack). Architecture per [ADR-0018](../adr/0018-true-hybrid-ssr-web-architecture.md): every signed-in page is server-rendered per request; edge middleware guards auth and refreshes near-expiry tokens with `Set-Cookie`.

**Bottom line:** the SW must be a **static file emitted at build time into `public/`**. Anything that reaches `.open-next/assets` is served correctly by Cloudflare with SW-friendly headers, bypassing the Worker and the middleware entirely. Runtime SW generation (the Turbopack route-handler model) does not survive serverless packaging. The two viable paths are `@serwist/next` with a webpack build, or a hand-rolled/scripted SW that keeps Turbopack.

## Q1 — Does OpenNext emit and serve the SW correctly?

Yes, for a build-time SW in `public/`.

- OpenNext serves `public/` files and `_next/static` build files through Cloudflare's static assets feature, and "the worker doesn't run **in front** of static assets, so the `headers` option of `next.config.ts` doesn't apply" to them ([OpenNext caching docs](https://opennext.js.org/cloudflare/caching)). In this repo that is the `ASSETS` binding on `.open-next/assets` (`apps/web/wrangler.jsonc`).
- Cloudflare routing: "Cloudflare will first attempt to serve static assets if one matches the incoming request"; the Worker script is invoked only when no asset matches ([Workers static assets routing](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)). So `GET /sw.js` never touches the Worker or the Next.js middleware — the auth guard cannot block SW registration and needs no matcher exclusion for it.
- Default asset headers: `Content-Type` inferred from the file extension at upload; `Cache-Control: public, max-age=0, must-revalidate`; an `ETag` for revalidation ([Workers static assets headers](https://developers.cloudflare.com/workers/static-assets/headers/)). `max-age=0, must-revalidate` is exactly what a SW file wants — every browser update check revalidates and picks up a new deploy immediately.
- Custom headers, if ever needed, go in a `public/_headers` file, which Cloudflare parses and applies to asset responses ([headers docs](https://developers.cloudflare.com/workers/static-assets/headers/)); OpenNext itself recommends this file for `/_next/static/*` `Cache-Control: public,max-age=31536000,immutable` ([OpenNext caching docs](https://opennext.js.org/cloudflare/caching)).
- `Service-Worker-Allowed` is not needed: `public/sw.js` is served at the origin root, so its default scope is already `/`.
- Searches of the `opennextjs/opennextjs-cloudflare` issue tracker for "service worker", "serwist", "next-pwa", "pwa" found **no** SW-specific bugs ([issue search](https://github.com/opennextjs/opennextjs-cloudflare/issues)) — consistent with the SW being just another static asset on this platform. OpenNext has no PWA documentation either way.

What does **not** work: serving the SW from a Next.js route handler (the `@serwist/turbopack` model, `app/serwist/[path]/route.ts` via `createSerwistRoute()` — [Serwist Turbopack docs](https://serwist.pages.dev/docs/next/turbo)). That compiles the SW and builds the precache manifest at request time; on Vercel it throws `ERR_MODULE_NOT_FOUND` for `next/dist/server/config.js` (hidden from output-file tracing by a `webpackIgnore` comment) and, even when traced, `.next/static/` and `public/` are not present in the function environment, so the manifest would be empty ([serwist#360](https://github.com/serwist/serwist/issues/360)). The OpenNext Worker bundle has the same properties (no `public/` or raw `.next/static` on the server side — they live in the assets store), and workerd cannot run the native esbuild binary the route uses. Treat the Turbopack route-handler integration as unusable on OpenNext/Cloudflare until Serwist ships build-time emission.

## Q2 — Coexistence with SSR pages and the edge middleware (ADR-0018)

The mechanics:

- A SW intercepts navigations **before** they reach the network. Any navigation the SW answers from cache never reaches Cloudflare, so the middleware's auth guard and token refresh do not run, and no `Set-Cookie` can be issued (the SW Cache API stores response bodies/headers, it cannot refresh cookies).
- This app's signed-in HTML is per-user, per-request (ADR-0018). A classic "app-shell precache" that serves cached HTML for navigations would (a) bypass the token-refresh middleware, letting sessions expire mid-use, and (b) risk showing stale or cross-session data.
- Therefore the correct shape for this architecture is: **network-only (or network-first) navigations + a precached offline fallback document**, not a cached app shell. Serwist supports this directly: the `fallbacks` option "precaches routes so that they can be used as a fallback when a `Strategy` fails to generate a response", and `navigationPreload` "enables navigation preloading if it is supported" so the network navigation is not delayed by SW startup ([Serwist class docs](https://serwist.pages.dev/docs/serwist/core/serwist)). Online behavior is byte-identical to today — middleware sees every navigation; offline, the user gets a designed fallback page instead of the browser dinosaur.
- Runtime caching is safe for immutable assets (`/_next/static/*`, fonts, icons) and can optionally be extended to API GETs later; cookies still flow on all network requests, so the dual-JWT cookie extractor is unaffected.
- Because assets are served before the Worker runs (Q1), the middleware never sees `/sw.js`, `/manifest.json`, or `/_next/static/*` regardless of its matcher — no matcher surgery is required for the SW itself. (The inverse also holds: middleware cannot add headers to those files; use `public/_headers` — [OpenNext caching docs](https://opennext.js.org/cloudflare/caching).)

## Q3 — Precache versioning across deploys

- **How the manifest is built:** `@serwist/next` injects a precache manifest at build time at the `injectionPoint` (default `self.__SW_MANIFEST`) in your `swSrc` (e.g. `app/sw.ts`) and emits the compiled worker to `swDest` (`public/sw.js`); entries carry revisions so outdated cached responses are replaced ([Serwist getting started](https://serwist.pages.dev/docs/next/getting-started)). The docs have you gitignore `public/sw*`, confirming build-time emission.
- **Update cycle:** the browser re-fetches `sw.js` on navigation/update checks; Cloudflare's `max-age=0, must-revalidate` + ETag on assets ([headers docs](https://developers.cloudflare.com/workers/static-assets/headers/)) means a new deploy's SW is detected on the next check. The new SW's install step downloads changed precache entries; `skipWaiting` "forces the waiting service worker to become the active one" and `clientsClaim` "claims any currently available clients" ([Serwist class docs](https://serwist.pages.dev/docs/serwist/core/serwist)) — with both set, the new precache goes live without requiring every tab to close.
- **Version skew:** a Workers deploy atomically replaces the asset manifest, so a client running the previous build's JS will 404 on old hashed `/_next/static` chunks it lazy-loads afterwards. This is the standard Next.js skew problem; on Cloudflare it is documented by OpenNext's **experimental skew protection** (`cloudflare.skewProtection.enabled` in `open-next.config.ts`, routing old clients to previous Worker versions via preview URLs; defaults: 20 versions / 7 days; not available if the Worker hosts a Durable Object) ([OpenNext skew how-to](https://opennext.js.org/cloudflare/howtos/skew)). A known bug: skew-protection preview URLs returned 404 for static assets with Next 16.2's deterministic build IDs ([opennextjs-cloudflare#1183](https://github.com/opennextjs/opennextjs-cloudflare/issues/1183)).
- **Interaction with precache:** precaching actually *softens* skew for whatever is in the manifest — precached chunks were downloaded at install time and are served from the SW cache even after the server stops hosting them. Lazy chunks not in the manifest still 404 until the client picks up the new SW/build. Practical stance for a single-owner PWA: precache the shell assets + offline page, enable `skipWaiting`/`clientsClaim`, and skip OpenNext skew protection (experimental, and #1183) unless mid-session 404s are observed.

## Q4 — Known OpenNext/Cloudflare-specific pitfalls

1. **Runtime SW generation fails on serverless** — `@serwist/turbopack`'s `createSerwistRoute` needs build artifacts and Next internals at request time; broken on Vercel ([serwist#360](https://github.com/serwist/serwist/issues/360)) and structurally incompatible with the OpenNext Worker bundle. Related young-package bugs: manifest not injected ([serwist#294](https://github.com/serwist/serwist/issues/294)), public assets precached from the wrong folder ([serwist#339](https://github.com/serwist/serwist/issues/339)), missing `"use client"` in `SerwistProvider` hard-500s Server Components ([serwist#357](https://github.com/serwist/serwist/issues/357)), `next dev --turbo` support still an open request ([serwist#54](https://github.com/serwist/serwist/issues/54)).
2. **Turbopack is the Next 16 default and does not run webpack plugins** ([Next.js Turbopack docs](https://nextjs.org/docs/app/api-reference/turbopack)). Using `@serwist/next` means adding a `build` script of `next build --webpack` to `apps/web` (OpenNext runs the package's build script). That works today but rides the legacy bundler path.
3. **`next.config` `headers()` and middleware do not apply to static assets** on this platform ([OpenNext caching docs](https://opennext.js.org/cloudflare/caching)); asset headers belong in `public/_headers` ([Cloudflare headers docs](https://developers.cloudflare.com/workers/static-assets/headers/)). Do **not** add long-lived `Cache-Control` for `sw.js` when adding the recommended immutable rule for `/_next/static/*`.
4. **`run_worker_first` would put middleware in front of `sw.js`** ([Cloudflare routing docs](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)). This repo does not set it; keep it that way, or exclude SW/manifest paths if it is ever enabled.
5. **Deploy skew 404s** on old hashed chunks; OpenNext skew protection is experimental and had an assets-404 bug with Next 16.2 deterministic build IDs ([opennextjs-cloudflare#1183](https://github.com/opennextjs/opennextjs-cloudflare/issues/1183), [skew how-to](https://opennext.js.org/cloudflare/howtos/skew)).
6. **next-pwa is dead** (2022 release, [repo](https://github.com/shadowwalker/next-pwa)); the maintained fork's own README redirects to Serwist ([@ducanh2912/next-pwa README](https://github.com/DuCanhGH/next-pwa/blob/master/packages/next-pwa/README.md)). Neither should be adopted in 2026.
7. **No OpenNext-emitted SW exists** — OpenNext neither generates nor documents a service worker; whatever is chosen, the SW is the app's responsibility and must land in `public/` before `opennextjs-cloudflare build` packages `.open-next/assets`. (Absence verified by docs and issue-tracker search; no positive statement exists — **unverified beyond absence of evidence**.)

## Recommendation for rv-checklist

- **Runtime model (independent of tooling):** no HTML app-shell cache. Navigations stay network-only with `navigationPreload`; precache `/~offline` + shell static assets; serve `/~offline` via Serwist `fallbacks` when navigation fetch fails; cache-first runtime caching for `/_next/static/*` and icons. This preserves ADR-0018's per-request SSR and the middleware token refresh exactly, while adding offline resilience.
- **Tooling, two acceptable paths:**
  1. **`@serwist/next` + `next build --webpack`** — least code, first-party docs, proven emission to `public/sw.js`; cost: pins the web build to the deprecated webpack path.
  2. **Hand-rolled build step on the `serwist` runtime library** — a small script (esbuild) that runs after `next build`, injects a manifest (hashed `.next/static` files + selected `public/` files) into `app/sw.ts`, and writes the compiled worker into `.open-next/assets/sw.js` (or into `public/` before `opennextjs-cloudflare build` packages the assets). Keeps Turbopack; cost: roughly 100 lines of build glue owned by this repo. This mirrors the workaround validated in [serwist#360](https://github.com/serwist/serwist/issues/360).
- Prefer path 1 for now (smallest surface, easy to migrate to `@serwist/turbopack` once it emits at build time); revisit when Serwist lands build-time Turbopack emission ([serwist#54](https://github.com/serwist/serwist/issues/54) and the `@serwist/turbopack` issue stream are the things to watch).
