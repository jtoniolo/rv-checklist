# Local-first sync engine landscape for this stack

**Ticket:** [#126](https://github.com/jtoniolo/rv-checklist/issues/126) (part of #124)
**Date compiled:** 2026-08-20
**Stack under evaluation:** NestJS + Postgres + TypeORM REST API, self-hosted homelab; Next.js web client with RTK Query hooks-only components (ADR-0011, ADR-0018); single owner; tiny data volume.
**Source policy:** Primary sources only — official docs, licence files, GitHub/npm registry metadata. Each claim carries its source.

**Hard requirements checked for every option:**

- Conflict model must support **newest-wins** (last-write-wins) **and** **additive deltas** (a running-total counter where concurrent "increment by 3" operations merge, not overwrite).
- Must coexist with the **RTK Query hooks-only** component rule: components call only generated RTK Query hooks. RTK Query supports non-HTTP data sources via `queryFn` ("RTK Query is really about tracking loading state and cached values for any async request/response sequence, not just HTTP requests" — [customizing-queries](https://redux-toolkit.js.org/rtk-query/usage/customizing-queries)) and push-based cache updates via `onCacheEntryAdded` + `updateCachedData` (Immer draft of the cached value) — [streaming-updates](https://redux-toolkit.js.org/rtk-query/usage/streaming-updates). Any engine whose client exposes a plain subscribe/observable API can therefore feed the RTK Query cache without changing components.

## 1. Hand-rolled outbox + IndexedDB (Dexie) replaying REST calls

- **Server-side requirements:** none beyond the existing NestJS + Postgres API. The browser queues writes in IndexedDB and replays your own REST calls. You write the queue, replay, and idempotency logic.
- **Licence/cost:** Dexie.js is Apache-2.0, free ([github.com/dexie/Dexie.js](https://github.com/dexie/Dexie.js), [npm dexie](https://registry.npmjs.org/dexie/latest)). **Dexie Cloud is not a free path:** the sync server is closed source; self-host licences are paid one-time — Business €3,495 (Docker binary only), Enterprise €7,995 (full source) ([dexie.org/cloud](https://dexie.org/cloud/), [dexie.org/pricing](https://dexie.org/pricing)). Dexie Cloud runs "on Node.js + PostgreSQL" and uses CRDT-based conflict resolution ([dexie.org/cloud](https://dexie.org/cloud/)). **Dexie.Syncable is dead** — its README says the package "has been unmaintained for a looong time and might be retired" ([addons/Dexie.Syncable](https://github.com/dexie/Dexie.js/tree/master/addons/Dexie.Syncable)). So the free Dexie path is fully hand-rolled.
- **Self-hosting fit:** perfect. No new containers; the client talks to the same NestJS API.
- **Conflict model:** entirely your code. (a) Newest-wins: compare `updatedAt` server-side or replay in order. (b) Additive deltas: store **operations, not final states**, in the outbox, and expose delta endpoints on the API (e.g. `POST /counters/:id/increment {by: 3}`). The server applies the delta transactionally, so concurrent increments merge by construction. No library support; idempotency keys, retry ordering, and tombstones are all your responsibility.
- **Maturity:** Dexie.js created Feb 2014, 14,539 stars, last push 2026-08-17, v4.4.5 ([GitHub API](https://api.github.com/repos/dexie/Dexie.js)).
- **RTK Query coexistence:** the cleanest of all options. A `queryFn` can read Dexie first and fall back to network ([customizing-queries](https://redux-toolkit.js.org/rtk-query/usage/customizing-queries)); `onCacheEntryAdded` + `updateCachedData` pushes local-DB changes into the cache ([streaming-updates](https://redux-toolkit.js.org/rtk-query/usage/streaming-updates)). Components keep using only RTK Query hooks; mutations stay RTK Query mutations that write to the outbox.

## 2. RxDB

- **Server-side requirements:** no server product. You implement RxDB's replication protocol as endpoints on the existing NestJS API: a **pull handler** (documents after a checkpoint), a **push handler** (receives `newDocumentState` + `assumedMasterState` per doc, returns conflicting master states), and optionally a **pullStream** (SSE) for realtime ([replication](https://rxdb.info/replication.html), [replication-http](https://rxdb.info/replication-http.html) — "RxDB does not have a specific HTTP-replication plugin because the replication primitives plugin is simple enough"). Backend constraints: documents deterministically sortable by last write time; soft deletes via a `_deleted` flag. So: no new containers, but entities need checkpoint fields and soft deletes, plus 2–3 new NestJS endpoints.
- **Licence/cost:** core Apache-2.0 ([github.com/pubkey/rxdb](https://github.com/pubkey/rxdb)). Free: core, replication primitives, **Dexie-based browser storage**, memory storage. Premium (paid): official IndexedDB, OPFS, SQLite storages, encryption, fulltext — Pro $99/month billed annually, Pro Plus $239/month ([rxdb.info/premium](https://rxdb.info/premium/)). The free browser persistence path is the Dexie-based RxStorage — free RxDB uses Dexie underneath anyway.
- **Self-hosting fit:** good — replication endpoints live inside the existing NestJS container. Premium pricing is out of scope for a personal app; free tier suffices at this data volume.
- **Conflict model:** first-class, resolved on the client via `conflictHandler` ({`isEqual`, `resolve`} receiving `{realMasterState, newDocumentState}`). Default handler "will always drop the fork state and use the master state instead" (server-wins); newest-wins is a trivial timestamp-comparing handler. Custom merge is explicitly supported: "In your custom conflict handler you likely want to merge properties of the realMasterState and the newDocumentState" ([transactions-conflicts-revisions](https://rxdb.info/transactions-conflicts-revisions.html)). **Caveat for the counter:** the handler sees document *states*, not operations, so an additive merge must derive the delta from assumed vs fork state — workable but easy to get wrong.
- **Maturity:** created Dec 2016, 23,355 stars, last push 2026-08-20, v17.4.0 ([GitHub API](https://api.github.com/repos/pubkey/rxdb)).
- **RTK Query coexistence:** RxDB does not force its own hooks — `RxQuery.$` is an RxJS observable that "always has the current result-set as value" ([rx-query](https://rxdb.info/rx-query.html)). Subscribe to it inside `onCacheEntryAdded` and feed `updateCachedData`. Cost: two stacked caches (RxDB store + RTK Query cache), and mutations must be rerouted to RxDB writes, hollowing RTK Query out to a subscription adapter.

## 3. Replicache

- **Status first:** Replicache is in **maintenance mode** "after five years of development"; it is now free ("we no longer charge for its use") and open-sourced, and the team's focus is Zero, with users "encouraged to migrate to Zero as they're able" ([replicache.dev](https://replicache.dev/)). Code lives in `rocicorp/mono` `packages/replicache` at v15.2.1 under Apache-2.0 ([mono package.json](https://github.com/rocicorp/mono/blob/main/packages/replicache/package.json)); the original `rocicorp/replicache` repo is archived ([GitHub API](https://api.github.com/repos/rocicorp/replicache)). Note the npm `replicache@15.3.0` package still points its licence field at roci.dev/terms.html ([npm replicache](https://registry.npmjs.org/replicache/latest)).
- **Server-side requirements:** no extra processes. You implement two POST endpoints in the existing NestJS API: **push** ([server-push](https://doc.replicache.dev/reference/server-push)) — applies each mutation and advances a per-client `lastMutationID` in the same Postgres transaction ("the effects of a mutation and the corresponding update to the lastMutationID must be revealed atomically") — and **pull** ([server-pull](https://doc.replicache.dev/reference/server-pull)) returning `{cookie, lastMutationIDChanges, patch}`. Optional **poke**: "A Replicache poke carries no data – it's only a hint telling the client to pull soon" over SSE/WebSocket; without it clients poll (default 60 s) ([poke](https://doc.replicache.dev/byob/poke)). You add a few bookkeeping tables (client, client group, version/CVR) to the existing Postgres — no separate database or daemon.
- **Licence/cost:** free; Apache-2.0 in mono (see above).
- **Self-hosting fit:** excellent — endpoints inside NestJS, poke via SSE/WebSocket, nothing else to run.
- **Conflict model:** the mutator model is the best match for the counter requirement. Mutations are **re-executed on the server**, not state-overwritten: on rebase "a `reserveRoom` mutator when run locally... might find a room in state AVAILABLE" but "when run on the server, the mutator might find that the room status is already RESERVED" — the mutation logic decides ([how-it-works](https://doc.replicache.dev/concepts/how-it-works)). An `increment(by)` mutator merges concurrent increments by construction. Newest-wins is just a `set` mutator applied in server order.
- **Maturity:** proven (5 years), but frozen — no new features. Betting on it means accepting a dead-ended dependency with Zero as the exit.
- **RTK Query coexistence:** good. Replicache's `subscribe(body, {onData})` API is framework-agnostic ("each time the result of body changes, onData is fired again with the new result" — [API reference](https://doc.replicache.dev/api/classes/Replicache)); React `useSubscribe` is only a convenience. Pattern: `queryFn` does an initial `rep.query(...)`, `onCacheEntryAdded` subscribes and pushes results via `updateCachedData`; writes become mutation endpoints whose `queryFn` calls `rep.mutate.*`. Components keep generated RTK Query hooks.

## 4. Zero

- **Server-side requirements:** the heaviest. Deploy **zero-cache** — one or more **view-syncers** ("serving client queries using a SQLite replica") plus one **replication-manager** ("bridge between the Postgres replication stream and view-syncers") — alongside Postgres with `wal_level=logical` (Postgres **15.0+** — [connecting-to-postgres](https://zero.rocicorp.dev/docs/connecting-to-postgres)). zero-cache needs three DB connections: `ZERO_UPSTREAM_DB` ("must be a direct connection (not via pgbouncer)"), `ZERO_CVR_DB`, `ZERO_CHANGE_DB` (can share one Postgres instance), plus a persistent SQLite replica volume (`ZERO_REPLICA_FILE`). Custom mutators need a push endpoint registered via `ZERO_MUTATE_URL` — plain HTTP, can live in the NestJS app ([mutators](https://zero.rocicorp.dev/docs/mutators)). Docker image `rocicorp/zero:1.9.0`. Documented sizing: single node 1 vCPU / 2 GB; multi-node view-syncer 2 vCPU / 4 GB ([deployment](https://zero.rocicorp.dev/docs/deployment), [self-host](https://zero.rocicorp.dev/docs/self-host)).
- **Licence/cost:** Apache-2.0 ([github.com/rocicorp/mono](https://github.com/rocicorp/mono), [npm @rocicorp/zero](https://registry.npmjs.org/@rocicorp/zero/latest)). No paid tier required to self-host.
- **Self-hosting fit:** possible in a homelab (Docker), but it is multiple cooperating components and a logical-replication slot for an app with one user. Heavy relative to the problem.
- **Conflict model:** custom **mutators** run "initially... on the client, against the client-side datastore," then "your push endpoint runs the push protocol, executing the server-side mutator in a transaction against your database"; pending local mutations are rolled back and replaced by server results ([mutators](https://zero.rocicorp.dev/docs/mutators)). Server re-execution gives additive-counter merges exactly like Replicache. Without custom mutators, CRUD writes are last-write-wins.
- **Maturity:** GA March 2026 ("generally available and fully-supported", API "very stable from here on out") ([status](https://zero.rocicorp.dev/docs/status)); v1.9.0; repo `rocicorp/mono` 3,360 stars, created Feb 2023, pushed 2026-08-20 ([GitHub API](https://api.github.com/repos/rocicorp/mono)). GA is recent (~5 months). A hosted "Cloud Zero" is on the 2026 roadmap.
- **TypeORM note:** the Zero schema is a TypeScript file "usually generated from your backend schema"; generators exist for Drizzle and Prisma but **not TypeORM**, so `schema.ts` would be hand-written and hand-maintained beside the TypeORM entities ([zero-schema](https://zero.rocicorp.dev/docs/zero-schema)).
- **RTK Query coexistence:** technically feasible, architecturally the worst fit. The core API is framework-agnostic — `materialize()` views expose `addListener((rows, resultType) => ...)` ([queries](https://zero.rocicorp.dev/docs/queries)) — so a `queryFn` + `onCacheEntryAdded` adapter keeps components on RTK Query hooks. But Zero's value is its synced query engine (ZQL); hiding it behind RTK Query duplicates caching and discards the query model. Adopting Zero properly means amending ADR-0011, not coexisting with it.

## 5. PowerSync

- **Server-side requirements:** run the **powersync-service** container (`journeyapps/powersync-service` on Docker Hub — [self-hosting](https://docs.powersync.com/self-hosting/getting-started)) plus **bucket storage** for its internal state — MongoDB, or Postgres since service v1.3.8, which can be a second database on the existing Postgres server ([service setup](https://docs.powersync.com/self-hosting/installation/powersync-service-setup)). Source Postgres needs `wal_level=logical`, a replication user, and a publication named `powersync` (Postgres ≥ 11) ([database-setup](https://docs.powersync.com/installation/database-setup)). The existing NestJS API stays and handles all writes (below). Partial-sync config caveat: YAML "Sync Rules" are now labelled legacy, superseded by "Sync Streams" — supported, but mid-transition ([sync-rules](https://docs.powersync.com/usage/sync-rules)).
- **Licence/cost:** service is **FSL-1.1-ALv2** — Functional Source License: free for any "Permitted Purpose" excluding competing commercial offerings; each release converts to Apache-2.0 after two years ([LICENSE](https://github.com/powersync-ja/powersync-service/blob/main/LICENSE)). Personal homelab self-hosting is squarely permitted; the self-hosted "Open Edition" is free (cloud tiers: free tier with 2 GB synced/month, Pro from $49/mo — [pricing](https://www.powersync.com/pricing)). Client SDKs (`@powersync/web` v2.2.0) are Apache-2.0 ([npm](https://registry.npmjs.org/@powersync/web/latest), [github.com/powersync-ja/powersync-js](https://github.com/powersync-ja/powersync-js)).
- **Self-hosting fit:** one extra service container + a bucket-storage DB (can be the same Postgres) + logical replication config. Moderate, Docker-friendly.
- **Conflict model:** reads sync down via sync rules; **writes go up through your own API** — the client queues PUT/PATCH/DELETE ops and your `uploadData()` connector calls your backend, which "you have full control over" and must apply writes immediately ([writing-client-changes](https://docs.powersync.com/installation/app-backend-setup/writing-client-changes)). "The default behavior is essentially 'last write wins'… the last update (as received by the server) to each individual field wins", and "deletes always win"; "If you require different behavior to 'last write wins', implement custom conflict resolution" ([handling-update-conflicts](https://docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts), [custom-conflict-resolution](https://docs.powersync.com/handling-writes/custom-conflict-resolution)). **For the counter:** a PATCH carries the new value, not the delta, but the schema option `trackPreviousValues` (JS: `trackPrevious`) exposes old values via `CrudEntry.previousValues`, so the backend can compute `delta = new − old` and apply it additively. Native increment ops are only a possible future feature ("Future versions may include support for custom operations, e.g. 'increment column by 1'"); CRDT payloads (e.g. Yjs) can be stored and synced today. So: newest-wins by default, additive deltas in your own upload path — same trick as the hand-rolled outbox, but the offline queue/retry machinery is provided.
- **Maturity:** service repo created May 2024, 373 stars, pushed 2026-08-20; SDK repo Apache-2.0, 709 stars, active ([GitHub API](https://api.github.com/repos/powersync-ja/powersync-service)). Commercial company behind it; cloud offering plus Open/Enterprise self-hosted editions.
- **RTK Query coexistence:** the web SDK is SQLite-in-browser (wa-sqlite) with framework-agnostic watch queries; React hooks are optional. Watched queries can feed `onCacheEntryAdded`/`updateCachedData` streams, keeping components on RTK Query hooks — same adapter shape (and same dual-cache cost) as RxDB.

## 6. ElectricSQL

- **Note:** evaluated the current rewrite (HTTP "Shapes" read-path sync), not the deprecated active-active PGlite version. The docs domain now redirects electric-sql.com → electric.ax.
- **Server-side requirements:** run the **Electric sync service** — "an Elixir web service, packaged using Docker" (`electricsql/electric`, port 3000) — against Postgres ≥ 14 with logical replication enabled (`wal_level=logical`) and a `REPLICATION`-role user; Electric creates publication `electric_publication_default` and slot `electric_slot_default` ([installation](https://electric.ax/docs/guides/installation), [deployment](https://electric.ax/docs/guides/deployment)). No companion database: shape logs and metadata live on the filesystem (`ELECTRIC_STORAGE_DIR` volume); it "trades storage for low memory use". Production guidance: proxy Shape requests through your own backend for auth ([react integration](https://electric.ax/docs/integrations/react)). Writes remain on the existing NestJS API.
- **Licence/cost:** Apache-2.0, 10,327 stars ([github.com/electric-sql/electric](https://github.com/electric-sql/electric)); client `@electric-sql/client` v1.5.26 Apache-2.0 ([npm](https://registry.npmjs.org/@electric-sql/client/latest)). Self-hosting is free with no feature gate; Electric Cloud is the optional paid managed service (PAYG $0 base, $1 per 1M writes; Pro $249/mo — [pricing](https://electric.ax/pricing)).
- **Self-hosting fit:** one extra container + logical replication config. Light-moderate.
- **Conflict model:** Electric is explicitly **read-path only**: "Electric does read-path sync... Electric does not do write-path sync" ([writes guide](https://electric.ax/docs/guides/writes)). Writes use one of four patterns (online writes; optimistic state; shared persistent optimistic state; through-the-database sync). Because every write goes through your own API, additive-delta endpoints work exactly as in the hand-rolled option; reads are server-authoritative (Postgres state wins, i.e. newest-wins as ordered by your API). **Important:** for offline write queueing you still hand-roll the outbox (pattern 3) — Electric only replaces the *read* refresh machinery.
- **Maturity:** repo since June 2022 (current HTTP/Shapes rewrite, old active-active architecture is gone); GA 1.0 released 2025-03-17; `@core/sync-service` 1.7.11 (2026-08-12), actively released ([releases](https://github.com/electric-sql/electric/releases)). TanStack DB is the flagship client store: its Electric collection `onInsert/onUpdate/onDelete` handlers persist to your backend and return a Postgres `txid` so optimistic state drops when the confirmed change arrives in the stream ([electric-collection](https://tanstack.com/db/latest/docs/collections/electric-collection)) — optional here.
- **RTK Query coexistence:** good. `ShapeStream`/`Shape` are framework-agnostic with `subscribe` methods intended for binding to other state libraries; `useShape` is optional ([react integration](https://electric.ax/docs/integrations/react)). A Shape subscription inside `onCacheEntryAdded` keeps read caches live without touching components.

## Assessment for this repo

The counter requirement is the discriminator: **additive deltas merge correctly only where code re-applies operations** — a hand-rolled delta endpoint (options 1, 5, 6), a re-executed mutator (3, 4), or a custom client-side conflict handler (2). Every option can do newest-wins.

- **Best fit: option 1 (Dexie outbox + delta-aware REST endpoints).** Zero new infrastructure, zero licence exposure, keeps ADR-0011 intact — RTK Query stays the single client cache via `queryFn` + `onCacheEntryAdded`. The cost (hand-rolled idempotency/ordering) is bounded because the data volume is tiny and single-owner, so conflicts are rare and the entity count is small.
- **Runner-up if a real protocol is wanted without new containers:** Replicache (mutator model is ideal for the counter, but maintenance mode) or RxDB (maintained and free, but state-based conflict handling and a dual-cache adapter).
- **PowerSync / Electric** are the credible "grown-up" paths; both keep write authority in the NestJS API (so the delta counter is easy) but each adds a sync container plus `wal_level=logical`, and Electric still leaves the offline write queue to you.
- **Zero** is the strongest engine technically but the worst organizational fit: multi-component infra for one user, and it wants to replace, not feed, the RTK Query layer.
